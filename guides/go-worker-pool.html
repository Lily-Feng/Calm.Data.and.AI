Representative problem

Process 100,000 jobs concurrently without opening 100,000 database connections. Design a Go worker pool.

Reasoning model

How to approach it

  1. Choose the worker limit from the downstream resource, not CPU count alone.
  2. One producer owns and closes the jobs channel; workers only receive.
  3. Use a WaitGroup to know when workers finish, then close results from a coordinator.
  4. Propagate context cancellation and return structured errors.
Failure modes

What breaks the model

  • Letting receivers close a shared channel.
  • Waiting for workers before draining an unbuffered results channel.
  • Spawning one goroutine per item and calling it a worker pool.
Core synthesis

What to remember

The pool bounds pressure on the database. A producer sends jobs and is the only owner that closes the jobs channel. N workers range over jobs and respect context cancellation. A separate coordinator waits for the workers and closes results, allowing the caller to range until completion without guessing counts. The worker number is tuned against connection limits and observed latency.

go reference 
func run(ctx context.Context, jobs <-chan Job, workers int) <-chan Result {
    results := make(chan Result)
    var wg sync.WaitGroup
    wg.Add(workers)
    for i := 0; i < workers; i++ {
        go func() {
            defer wg.Done()
            for job := range jobs {
                select {
                case results <- process(job):
                case <-ctx.Done(): return
                }
            }
        }()
    }
    go func() { wg.Wait(); close(results) }()
    return results
}
