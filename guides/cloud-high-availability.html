Representative problem

A customer-facing API must survive a zonal failure and recover from a regional failure with minimal data loss. Walk through your design.

Reasoning model

How to approach it

  1. Start with explicit SLOs: target availability, RTO, RPO, and consistency needs.
  2. Spread stateless compute across zones behind a health-aware load balancer.
  3. Choose regional replication for data, then explain failover and split-brain controls.
  4. Add cross-region traffic routing, tested backups, and a rehearsed recovery runbook.
Failure modes

What breaks the model

  • Calling multi-zone the same as multi-region.
  • Claiming zero RPO without synchronous cross-region writes and their latency cost.
  • Designing failover that has never been exercised.
Core synthesis

What to remember

I would make the normal path resilient to a zonal outage first, because it is the cheaper and more frequent failure domain. A separate regional recovery path is driven by the required RTO and RPO. Stateless services can be warm or active-active, while the data strategy depends on consistency. DNS or global routing is only the switch; replicated state, idempotent writes, and rehearsed recovery make the design credible.

Platform translation

Same pattern, different names

  • AWS: ALB + Multi-AZ compute + Aurora Global Database / DynamoDB global tables
  • Azure: Front Door + zone-redundant compute + Cosmos DB multi-region / SQL failover groups
  • GCP: Global external load balancer + regional MIG/GKE + Spanner / cross-region database replica
