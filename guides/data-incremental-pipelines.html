Representative problem

A daily full refresh no longer finishes in its window. Redesign it for incremental processing while preserving correctness.

Reasoning model

How to approach it

  1. Identify a trustworthy change signal: log sequence, commit version, update timestamp, or source CDC.
  2. Persist the processing boundary and make each write idempotent with MERGE or append plus deduplication.
  3. Define late-arrival and deletion behavior explicitly.
  4. Add reconciliation: source counts, freshness, duplicates, and periodic backfill tests.
Failure modes

What breaks the model

  • Using timestamps without overlap or clock-skew protection.
  • Advancing the checkpoint before the target commit succeeds.
  • Ignoring deletes and schema evolution.
Core synthesis

What to remember

I choose a monotonic source boundary when possible, store it only after a successful target commit, and make replay safe. Each batch reads an overlap or version range, deduplicates by business key and sequence, and merges into the target. Late events have a defined watermark or correction path. Reconciliation metrics prove that the faster pipeline is still complete.

Platform translation

Same pattern, different names

  • Databricks: Auto Loader / streaming tables + checkpoints + Delta MERGE
  • Snowflake: streams + tasks / dynamic tables + MERGE
  • Fabric: pipelines / Dataflow Gen2 + incremental refresh + Delta tables in OneLake
