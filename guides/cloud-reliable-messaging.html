Representative problem

Orders are processed asynchronously. Consumers sometimes crash after charging a card but before acknowledging the message. Prevent double charges without losing orders.

Reasoning model

How to approach it

  1. Assume at-least-once delivery and make the business operation idempotent.
  2. Store an idempotency key with the durable transaction before acknowledging the message.
  3. Use bounded retries with jitter, then isolate poison messages in a dead-letter queue.
  4. Expose queue age, retry count, dead-letter volume, and processing latency.
Failure modes

What breaks the model

  • Promising exactly-once behavior end to end.
  • Retrying immediately and amplifying an outage.
  • Using an in-memory deduplication cache as the source of truth.
Core synthesis

What to remember

The broker can redeliver, so the consumer must make the charge operation idempotent. I use an order or payment attempt ID as the idempotency key and persist the result atomically with the local state transition. A duplicate returns the stored result. Retries are bounded and delayed; poison messages move to a dead-letter queue with enough context to replay safely.

Platform translation

Same pattern, different names

  • AWS: SQS/SNS or EventBridge + DLQ
  • Azure: Service Bus queues/topics + dead-letter subqueue
  • GCP: Pub/Sub + dead-letter topic
